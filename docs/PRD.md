## 0-1. 기능명세서

0절 표를 기능 단위로 풀어 쓴 것이다. 기준은 2026-10-03 시점의 코드다.

- **main** = `origin/main`. Flutter 화면(`frontend/lib/`)과 AI 모듈(`backend/app/ai/` 의 enrich·poster·profile·requirements·recommend·mask)이 있다. AI 모듈은 `HC` 브랜치에도 같은 파일이 있다.
- 서버 코드(`backend/app/collectors/`, `features/`, `jobs/`)도 main 에 있다. 아래 「백엔드 브랜치」라는 말은 처음 서버를 만든 브랜치를 가리키던 표기이고, 지금은 main 의 같은 경로를 뜻한다. 수집·첨부·요약·API 서버(`backend/app/`)가 있다. 이 브랜치의 `backend/app/ai/` 에는 서버 전용 `digest.py`·`verify.py`·`llm.py` 가 있다.
- 상태: **구현** = 실제 서버나 기기에서 동작한다. **부분** = 화면이나 함수는 있지만 mock·데모 데이터를 쓰거나 서로 연결되지 않았다. **다음 단계** = 코드가 없다.
- 처리 칸의 (코드)는 같은 입력이면 같은 결과가 나오는 규칙이고, (AI)는 LLM 호출이다.

### 주요 기능 상세

#### F-01 공지 수집

- **정상 흐름**
  1. 서버가 켜지면 스케줄러가 `POLL_INTERVAL_MIN`(기본 10분)마다 한 바퀴를 돈다. 운영자는 `POST /api/admin/poll-now` 로 바로 돌릴 수 있다.
  2. 출처 6곳의 목록을 순서대로 읽는다. 요청 사이는 1초 띄우고, 수집기 이름을 User-Agent에 밝힌다.
  3. 이미 저장한 글을 빼고, 출처마다 새 글을 최대 `NEW_PER_SOURCE`(기본 8)건 고른다.
  4. 상세 본문과 첨부 글자를 모아(F-02) DB에 pending으로 저장한 뒤 요약(F-03)으로 넘긴다.
- **예외 처리**
  - 한 바퀴가 도는 중에 다시 부르면 건너뛴다(잠금). 스케줄러와 수동 수집이 겹치지 않는다.
  - 목록이나 상세를 못 받으면 그 출처나 그 글만 건너뛰고 `poll-status` 의 errors에 남긴다. 이전에 저장한 데이터는 그대로 둔다.
  - 첨부 하나를 못 받아도 글 전체를 버리지 않고 그 첨부에 「다운로드 실패」 사유를 붙인다.
- **수용 기준**
  - `POST /api/admin/poll-now` 다음에 `GET /api/admin/poll-status` 의 저장 글 수가 늘고, `GET /api/sources` 가 6개를 돌려준다.
  - 백엔드 브랜치에는 수집기 자동 테스트가 없다. 위 기준은 손으로 확인한다.

#### F-03 AI 요약·분류·마감 (근거 검사)

- **정상 흐름**
  1. 본문과 첨부 글(파일당 12,000자)을 한 입력으로 묶고, 학번 형태를 `[학번]` 으로 가린 뒤 3만 자로 자른다.
  2. 프롬프트 파일과 JSON 스키마로 LLM을 부른다(서버는 `llm.py` 한 곳에서 호출하고 180초 제한을 둔다).
  3. 코드가 결과를 검사한다. 핵심·준비물·마감·마지막 날짜는 근거 문장이 입력 글에 있어야 남는다(공백·문장부호만 다른 것은 통과). 날짜는 ISO 형식이어야 하고, 분류는 고정 6개 안에서 2개까지 남긴다.
  4. 통과한 결과를 `digest.status="done"` 으로 저장한다.
- **예외 처리**
  - 호출 실패나 형식 오류는 1회 다시 부른다. 그래도 실패하면 `status="failed"` 와 오류 문구를 저장하고, 분류는 출처 기본값을 쓴다. 화면은 「AI 분석을 완료하지 못했어요」를 띄운다.
  - 근거가 없는 마감은 null이 되고, 화면은 「원문 확인」으로 표시한다.
  - 프롬프트를 바꾸면 `POST /api/admin/redigest` 로 저장된 글을 다시 요약한다.
  - AI 모듈(main `enrich.py`)은 키(`KMU_AI_API_KEY`)가 없으면 LLM을 만들 때 오류로 멈춘다. 평가 스크립트는 `--yes` 가 없으면 호출 수만 알리고 멈춘다.
- **수용 기준**
  - main `backend/app/ai/tests/test_enrich.py` 의 `test_evidence_not_in_text_is_dropped`, `test_two_bad_answers_fail_with_board_default` 가 통과한다. AI 모듈 테스트 전체는 159개 통과, 17개 건너뜀이다(2026-10-03, LLM 없이 실행). 건너뛴 17개는 공지 본문 캐시(`eval/.cache`, 커밋 안 함)가 있어야 도는 테스트이고, `fetch_bodies` 로 캐시를 받으면 176개가 모두 통과한다.
  - 실측(AI 모듈, 표본 20건): 본문 공지 14건에서 AI 14/14, LLM 없는 기준선 4/14다. 포스터 공지까지 합쳐 실제 마감이 있는 16건은 AI 16/16, 기준선 4/16이다. 정답은 사람이 확인하기 전 초안이고 프롬프트를 이 표본으로 썼으므로 표본 안 점수다. 자세한 값은 `backend/app/ai/README.md`.
  - 서버의 `verify.py` 에는 자동 테스트가 없다.

#### F-05·F-06 분야 대시보드, 다중 선택, 검색

- **정상 흐름**
  1. `/feed` 에 들어가면 `GET /api/feed?sort=recommend` 로 전체 목록을 한 번 받는다.
  2. 글마다 분류·출처·제목 키워드로 분야 6개 중 하나 이상에 배정하고, 타일에 개수와 미리보기를 보여 준다.
  3. 타일을 여러 개 고르면 고른 분야 중 하나라도 맞는 글이 보인다. 검색어·출처·정렬은 이 목록 위에서 화면이 거른다.
  4. 정렬을 바꾸면 서버에서 다시 받는다. 마감 임박 순은 마감 모르는 글을 뒤로 보낸다.
- **예외 처리**
  - 서버 응답이 없거나 20초를 넘기면 「공고를 불러오지 못했어요. 연결을 확인해 주세요.」를 띄운다. 정렬을 빨리 바꿔도 늦게 온 이전 응답은 버린다.
  - 어느 분야에도 안 맞는 글은 「기타」로 간다.
  - 추천 순에서는 마감이 지난 글을 숨긴다. 로그인해서 구독이 있으면 서버가 AI 추천도 순(F-19)으로 주고, 없으면 최신순이다.
- **수용 기준**
  - 검색어 「SW사업단 장학」은 출처 별칭과 분류가 모두 들어 있는 글만 남긴다(`notice_search.dart` 의 단어별 AND 규칙).
  - 피드·검색에는 Flutter 자동 테스트가 없다. `?demo=1` 데이터로 손으로 확인한다.

#### F-08 지원 준비 패널

- **정상 흐름**
  1. 공지 상세 아래에서 그 공지의 필요 항목을 불러온다.
  2. AI가 공고 문장에서 필요 항목과 서류를 고르고, 항목 키는 고정 12개(`name`, `phone`, `email` 등) 안에서만 쓴다.
  3. 코드가 근거 문장이 원문에 없는 항목과 목록 밖 키를 버린다.
  4. 화면이 기기에 저장된 내 값(F-09)을 항목 옆에 놓고 복사 버튼을 준다. 제출은 사용자가 원래 사이트에서 직접 한다.
- **예외 처리**
  - 불러오기에 실패하면 「준비 목록을 불러오지 못했어요. 원문에서 확인해 주세요.」를 띄우고, 다음에 다시 부를 수 있게 캐시를 지운다.
  - 남은 항목이 없으면 「근거가 있는 준비 목록이 없어요. 원문을 확인해 주세요.」를 띄운다.
  - AI가 두 번 다 실패하면 `status="failed"` 와 빈 목록을 돌려준다.
  - 클립보드 복사가 실패하면 직접 선택하라고 안내한다.
- **수용 기준**
  - main `backend/app/ai/tests/test_requirements.py` 의 `test_evidence_not_in_text_drops_only_that_item`, `test_unknown_key_drops_only_that_item` 이 통과한다.
  - 서버에 `GET /api/notices/{id}/requirements` 가 없어서 지금은 `?demo=1` 데이터로만 화면이 채워진다.

#### F-10·F-11 가입·동의·온보딩

  3. 학과·학년을 고르고, 관심 분야를 고르거나 자연어 한 줄로 적는다.
  4. 내 이력 화면으로 넘어가 저장한다.
- **예외 처리**

  - 탈퇴하면 서버 탈퇴 요청과 함께 기기의 이력·지원 정보를 지운다.
  - 지금은 `USE_MOCK=true` 라 계정·구독·자연어 해석이 앱 안의 mock으로 처리된다.
- **수용 기준**

#### F-13·F-14 포트폴리오 PDF 분석

- **정상 흐름**
  1. 선택 동의에 체크해야 PDF를 고를 수 있다.
  2. 브라우저 안에서 PDF 글자를 뽑는다. 원본은 저장하지 않는다.
  3. 전화번호·이메일·학번 형태를 가리고, 무엇을 몇 개 가렸는지 보여 준다.
  4. 가린 글만 분석으로 보내고, AI가 기술·태그·프로젝트·수상·활동을 근거와 함께 뽑는다.
  5. 검토 화면에서 사용자가 체크한 항목만 기기의 내 이력에 저장한다.
- **예외 처리**
  - 글자가 없는 PDF(스캔본)는 「글자를 읽을 수 없는 PDF예요」로 안내하고 직접 입력으로 보낸다. AI 함수도 30자 미만이면 부르지 않고 `no_text` 를 돌려준다.
  - 근거가 원문에 없는 항목과 태그 목록 밖의 태그는 버린다.
  - 이름과 생년월일은 자동으로 가리지 못한다. 올리기 전 화면에서 안내한다.
- **수용 기준**
  - `frontend/test/pii_masker_test.dart`, `pdf_extract_test.dart`, `profile_analysis_test.dart`, `profile_pages_test.dart`(체크를 끈 항목은 저장 안 함)가 통과한다(main).
  - main `backend/app/ai/tests/test_profile.py`, `test_mask.py` 가 통과한다.
  - 서버에 `POST /api/profile/analyze` 가 없어서 지금 화면의 분석 결과는 예시값이다. 가리기(3번)까지는 실제로 동작한다.

#### F-15 나의 상황 브리핑

- **정상 흐름**
  1. 학과·학년·신분·졸업 예정 여부·관심 분류를 보낸다. 서버는 이 값을 저장하지 않고, 이름·학번·연락처는 받지 않는다.
  2. 요약이 끝난 글 중에서 할 일이 있고, 마감이 안 지났고, 대상 조건이 맞고, 관심 분류나 필수 분류(학사·생활, 졸업)인 글만 고른다.
  3. 마감 임박 순으로 놓고, 출처만 다른 같은 공지는 하나로 합친다.
  4. 글마다 「마감 D-3」 같은 이유를 코드가 붙인다.
- **예외 처리**
  - 마감을 모르면 마지막 관련 날짜로 판단하고, 그것도 없으면 최근 30일 안에 올라온 글만 남긴다.
  - 대상 조건이 비어 있으면 모두 대상으로 본다.
  - 요약이 failed이거나 pending인 글은 넣지 않는다.
- **수용 기준**
  - 같은 상황과 같은 DB에서 `POST /api/briefing` 을 두 번 부르면 같은 순서가 나온다(AI를 부르지 않는 코드 규칙).
  - 자동 테스트는 없다. 화면에서 아직 부르지 않으므로 상태는 「부분」이다.

### 담당

백엔드 서버(수집·첨부·요약·API, 백엔드 브랜치 `backend/`)는 해서, 가입·온보딩·내 이력·지원 정보 화면(`frontend/lib/features/auth/`, `onboarding/`, `profile/`)은 택준, 피드·상세·지원 준비 화면(`frontend/lib/features/feed/`, `notice/`, `apply_helper/`)은 민섭, AI 모듈(main `backend/app/ai/`)과 문서(`docs/`)는 현찬이 맡는다.

## 1. 한 문장 정의

국민대 재학생이 학교 본부·단과대 공지와 공모전·대외활동·채용 소식을 여러 사이트에서 찾아다니는 귀찮음, 그리고 지원할 때마다 같은 기본 정보를 다시 적는 귀찮음을 AI가 대신한다. AI는 새 글을 읽고 분류·요약하고, **내 관심 분야와 이력에 맞는 글만** 골라 알려 주고, 공고마다 내야 할 정보 목록을 뽑아 내 정보로 채워 준다.

## 2. 문제 (WHO)

- **출처가 흩어져 있다.** 학교 본부 공지만 해도 카테고리가 학사·행정·특강·장학·사회봉사·공모·행사·교내채용·교외채용·시스템 등으로 나뉘어 있다(학교 홈페이지 메뉴에서 확인함). 단과대학 등 17곳은 홈페이지가 각자 따로 있다(메인 링크 17개 확인함). 공지 게시판이 각각 따로 있는지는 소프트웨어융합대학만 확인했다. 공모전·대외활동은 외부 플랫폼에 또 따로 있다.
- **학교 공식 앱은 이 문제를 다 풀지 못한다.** App Store의 「국민대학교」 앱은 행정·학사·장학·입학 공지 알림을 제공한다. 그런데 마지막 업데이트가 2018-01-17이고(확인함), 단과대 공지와 외부 정보는 없다.
- **지원할 때마다 같은 정보를 다시 쓴다.** 공모전·대외활동·채용 지원서는 이름, 연락처, 학교·학과·학년 같은 기본 항목을 매번 묻는다(팀원 경험이고, 공고 표본으로는 아직 확인하지 않았다).
- **근거.** 팀원이 직접 겪어서 낸 문제다. 몇 명이 겪는지는 아직 숫자가 없으니 현장 설문으로 확보한다(13절).

## 3. AI가 대신하는 것 (AI)

| 단계 | 하는 일 | 누가 판단하나 |
|---|---|---|
| 수집 | 새 글 감지, 본문 텍스트 저장 | 코드 |
| 분류 | 분야 태그(장학, 공모전 등)와 대상(학년·전공) 추출 | AI. 게시판 기본값을 출발점으로 삼는다 |
| 요약 | 3줄 요약, 마감일·신청 방법 추출 | AI. 근거 문장도 같이 낸다 |
| 자연어 구독 | "AI 관련 공모전이랑 장학금, 3학년"을 필터 조건으로 바꿈 | AI가 해석하고, 실제 필터링은 코드가 한다 |
| 이력 정리 | 포트폴리오 PDF에서 활동·수상·기술과 추천 태그를 뽑아 내 이력 칸을 채움 | AI. 선택 동의 후에만 하고, 사용자가 검토한 뒤 저장한다 |
| 맞춤 추천 | 공고 태그와 내 이력 태그가 겹치는 글을 위로 올림 | 순서는 코드가 정한다. 공고 태그는 AI가 붙이고, 내 태그는 사용자가 목록에서 고르거나 PDF 분석이 제안한다 |
| 지원 준비 | 공고 본문에서 내야 할 정보·서류 목록을 뽑아 내 정보 항목에 연결 | AI는 공고 문장만 읽는다. 내 개인정보 값은 AI에 보내지 않고, 채우는 일은 화면 코드가 한다 |
| 필터·알림 | 구독 조건에 맞는 글만 피드와 알림으로 보냄 | 코드. 같은 입력이면 같은 결과가 나온다 |

규칙은 이렇다. AI는 해석만 하고, 걸러 내는 판단은 코드가 한다. AI가 모르는 값은 `null`로 둔다. 마감일은 원문에서 찾은 근거 문자열이 있을 때만 표시하고, 없으면 "원문 확인"으로 표시한다.

## 4. 돈 (MONEY): 가설과 검증

학생에게는 무료로 제공한다. 돈을 낼 쪽은 아래 두 가설이고, 둘 다 아직 근거 숫자가 없다. 발표에서도 가설이라고 밝힌다.

| 가설 | 누가 | 왜 내나 | 검증 방법 |
|---|---|---|---|
| H1 | 공모전·대외활동·채용 주최 측 | 국민대생 중 특정 학년·전공에게 정확히 노출된다 | 구독 데이터로 타깃 규모를 보여 줌(데모 수치) |
| H2 | 학교(학생처, 단과대 행정실) | 공지 도달률을 알 수 있다(몇 명이 구독하고 열람했나) | 발표 Q&A용 시나리오만 준비 |

현장 설문(13절)에 "이런 서비스를 쓰겠나"를 넣어서 WHO를 숫자로 만든다. MONEY는 숫자를 지어내지 않는다.

## 5. 사용자 흐름과 데모 화면 (역산)

발표에서 보여 줄 화면을 먼저 정하고, 여기에 없는 기능은 만들지 않는다. v0.2에서 1번, 2번의 이력 입력, 3번의 추천 순, 6번을 더했다(6-1절).

1. **가입·동의.** 닉네임과 비밀번호로 가입하고, 필수 동의를 받는다.
2. **온보딩.** 학과와 학년을 고르고 관심 분야 칩을 고른다. 자연어 입력칸도 있다. 내 이력은 직접 입력하거나, 포트폴리오 PDF를 올리면 AI가 채운 결과를 검토해서 저장한다.
3. **내 피드.** 고른 분야의 글만 나온다(구현: 대시보드에서 직접 고르기. 추천 순은 로그인 뒤 AI 추천도 순). 추천 순과 마감 임박 순을 바꿀 수 있다. 카드마다 AI 요약 3줄, 마감 배지, 추천 이유가 붙는다.
4. **알림 (다음 단계, 이번에 만들지 않음).** 새 글이 감지되면 휴대폰으로 알림이 온다(채널은 9절에서 결정).
5. **상세.** 요약, 마감일과 그 근거 문장, 신청 방법, 원문 링크를 보여 준다.
6. **지원 준비.** 상세 화면 안에 이 공고에 내야 할 정보·서류 목록이 나온다. 내 정보가 채워진 칸마다 복사 버튼이 있고, 빠진 정보는 따로 표시한다.

**데모 대본 골격:** 문제(사이트 여러 개를 돌아다니는 화면) → 가입·동의 → 온보딩(가상 포트폴리오 PDF를 올리면 AI가 이력을 채움 → 검토) → "지금 수집" 버튼으로 실제 공지를 수집 → 추천 피드와 추천 이유 → 상세 → 지원 준비(복사, P3가 됐을 때만) → 알림 도착.

## 6. MVP 범위 (제안)

출처 범위는 16절에서 팀이 정한다. 아래는 오늘 마감 안에 끝까지 돌리기 위한 제안이다.

**오늘 만드는 것**

- 본부 공지 게시판 5개: 학사(4), 특강(6), 장학(7), 공모·행사(9), 교외채용(11). 괄호 안은 게시판 번호다. (실제 서버 수집은 학사(4)와 SW사업단, 소프트웨어융합대학 RSS다. AI 정확도 표본은 5개 게시판에서 받았다)
- 단과대 1곳: 소프트웨어융합대학 RSS. 여유가 있으면 1곳을 더한다.
- AI 분류·요약·마감 추출, 관심 분야 구독, 피드, 상세, 알림 채널 1개.
- 6-1절 P1~P3를 우선순위대로, 시간 안에 되는 데까지 만든다.

**오늘 안 만드는 것 (로드맵)**

- 이메일 인증, 비밀번호 찾기, 소셜 로그인. 닉네임 가입이라 비밀번호를 잊으면 복구할 수 없다.
- 외부 사이트 지원서에 자동 입력하거나 대신 제출하기.
- 전 단과대 수집, 네이티브 앱.
- 첨부파일(hwp, pdf) 본문 분석. (서버가 실제로는 만들었다. 0절)
- 외부 플랫폼 자동 수집 (8절에서 A안이나 B안을 고를 경우). 이유는 7·8절에 있다.

## 6-1. 추가 기능: 가입·동의·내 이력·맞춤 추천·지원 정보 채우기 (v0.2)

**현찬 제안 (두 가지, 팀 합의 여부는 미확인)**

- 닉네임과 비밀번호로 가입하고 개인정보 동의를 받는다. 그다음 공모전·취업 지원 때 매번 쓰는 개인정보를 AI가 자동으로 기록해 준다.
- 개인에게 맞는 공고를 추천하려면 이력이나 포트폴리오 기록이 필요하다. 사람이 직접 입력하거나, 포트폴리오 PDF를 올리면 AI가 분석해서 맞춰 적어 준다.

**판단.** 방향은 좋다.

- 맞춤 추천이 들어가면 AI 칸이 강해진다. "그냥 RSS 리더 아니에요?"라는 질문에 "내 이력을 읽고 공고를 골라 준다"로 답할 수 있다.
- 지원 준비까지 이어지면 「찾아만 주고 해결은 안 한다」는 지적을 막는다.

대신 그대로 만들면 두 가지가 위험하다.

- 개인정보(이름, 연락처, 학번, 이력)를 서버에 쌓거나 AI API로 보내는 순간 심사에서 보안·법 질문이 바로 나온다. 하루 만에 암호화, 접근 통제, 파기까지 제대로 만들기는 어렵다.
- 기능이 다섯 개(가입, 동의, 이력, 추천, 지원 준비)로 늘어난다. 백엔드가 1명이라 핵심 기능(공지·알림)이 미완성으로 끝날 수 있다.

그래서 아래 원칙과 우선순위로 줄여서 넣는 안을 제안한다. **이 절의 개인정보 처리 방식과, 이를 따르는 3·10·11·14·15절의 문장은 모두 제안이다.** 팀이 16절에서 다르게 정하면 같이 고친다.

**설계 원칙 (제안)**

1. 이름, 연락처, 학번 같은 지원용 개인정보 값은 **이 기기(브라우저)에만** 저장한다. 서버로도, AI로도 보내지 않는다.
2. 개인 자료가 AI로 가는 경우는 **포트폴리오 PDF 분석 하나뿐**이다. 선택 동의를 따로 받는다. 보내기 전에 전화번호·이메일·학번 형태의 글자를 브라우저에서 가린다. 원본 PDF와 보낸 글은 저장하지 않는다.
3. 추천은 **태그로** 한다. 공고와 내 이력 양쪽에 같은 태그 목록을 붙이고, 겹치는 정도로 순서를 정한다. 이력을 직접 입력할 때는 사용자가 태그 목록에서 고른다(AI를 거치지 않는다). 서버에는 이 태그만 올라간다. 순서를 매기는 건 코드라서 같은 입력이면 같은 결과가 나온다.
4. 서버에는 닉네임, 비밀번호 해시, 학과, 학년, 관심 분야, 추천 태그, 알림 등록 정보만 둔다.
5. 주민등록번호는 받지 않는다. 법령 근거 같은 예외 사유가 없으면 처리할 수 없다(개인정보 보호법 제24조의2, 검색 요약으로만 봄). 주소도 MVP에서는 받지 않는다.
6. 외부 사이트 지원서에 자동 입력하거나 대신 제출하지 않는다. 복사 버튼까지만 만들고, 제출은 본인이 한다.
7. 데모와 테스트에는 **지어낸 가상 인물** 정보와 가상 포트폴리오 PDF만 쓴다. 팀원의 실제 정보는 넣지 않는다.

**다루는 정보와 처리 위치**

| 항목 | 위험도 | 저장 위치 | AI로 보내나 | 비고 |
|---|---|---|---|---|
| 닉네임 | 낮음 | 서버 | 아니오 | 가입 화면에 실명을 쓰지 말라고 안내한다 |
| 비밀번호 | 높음(유출 시) | 서버, 해시만 | 아니오 | 평문 저장 금지. 비밀번호 전용 해시(bcrypt, argon2 등)를 쓴다 |
| 학과, 학년, 관심 분야 | 중간 | 서버 | 자연어 구독 해석 때만 | 이름·학번과 같은 곳에 두지 않는다 |
| 추천 태그 | 낮음 | 서버 | 아니오 | 고정 태그 목록에서 고른 값만 |
| 알림 등록 정보 | 중간 | 서버 | 아니오 | |
| 이름 | 높음 | 기기 | PDF 분석 때 가려지지 않을 수 있음 | 이름은 자동으로 가리기 어렵다. 올리기 전에 안내한다 |
| 전화번호, 이메일, 학번 | 높음 | 기기 | 아니오(PDF 분석 전에 가림) | |
| 생년월일 | 중간 | 기기 | PDF 분석 때 가려지지 않을 수 있음 | 자동 가리기 대상이 아니다. 이름과 합치면 개인이 특정된다 |
| 이력(활동, 수상, 프로젝트, 기술) | 중간 | 기기 | PDF 분석 때만, 선택 동의 후 | 결과는 사용자가 검토한 뒤 저장한다 |
| 포트폴리오 PDF 원본 | 높음 | 저장하지 않음 | 글자만 뽑아 가린 뒤 보냄 | 스캔 이미지 PDF는 글자가 없어 수기 입력으로 안내한다 |
| 주소 | 높음 | 받지 않음 | | MVP 제외 |
| 주민등록번호 | | 받지 않음 | | 예외 사유 없이 처리할 수 없다(제24조의2, 검색 요약으로만 봄) |

위험도는 넣기 전에 점검하려고 나눈 상대 구분이다. 최종 판단은 팀이 한다.

**동의 화면**

개인정보 보호법 제15조 제2항은 동의를 받을 때 목적, 항목, 보유·이용 기간, 거부 권리와 불이익을 알리라고 정한다(검색 요약으로만 봤고 법령 원문은 열지 않았다. 발표 전에 law.go.kr에서 확인한다). 동의는 두 개로 나눈다.

필수 동의 (가입 직후)

| 알릴 것 | 문구 초안 |
|---|---|
| 수집·이용 목적 | 관심 분야와 이력 태그에 맞춘 공지 추천과 알림 |
| 수집 항목 | 닉네임, 비밀번호(암호화 저장), 학과, 학년, 관심 분야, 추천 태그, 알림 등록 정보 |
| 보유·이용 기간 | 탈퇴할 때까지. 탈퇴하면 바로 지운다 |
| 거부 권리와 불이익 | 동의하지 않아도 공지 목록은 볼 수 있다. 맞춤 추천과 알림만 받을 수 없다 |

선택 동의 (포트폴리오 PDF를 올릴 때만)

| 알릴 것 | 문구 초안 |
|---|---|
| 수집·이용 목적 | 포트폴리오에서 활동·수상·기술을 뽑아 내 이력 칸을 채우기 |
| 수집 항목 | 올린 PDF에서 뽑은 글(전화번호·이메일·학번 형태는 가린 뒤) |
| 보유·이용 기간 | 저장하지 않는다. 분석이 끝나면 버리고, 결과는 이 기기에만 저장한다 |
| 거부 권리와 불이익 | 동의하지 않으면 이력을 직접 입력하면 된다 |
| 추가 고지 | 분석을 위해 외부 AI 서비스로 보낸다. 처리 위탁이나 국외 이전 고지가 필요한지는 **확인 필요** |

지원 정보(이름, 연락처 등)는 서버가 모으지 않으므로 필수 동의에 넣지 않는다. 대신 내 지원 정보 화면에 "이 정보는 이 기기에만 저장되고 서버로 보내지 않는다"는 안내를 둔다. 이 판단이 법적으로 맞는지는 검토받지 않았다.

**AI가 하는 일**

1. `extractProfile(가린 글) → 내 이력` (PDF 분석, 선택). 근거 구절이 없는 항목은 내지 않는다. 이름·연락처 칸은 만들지 않는다. 결과는 바로 저장하지 않고, 사용자가 검토·수정한 뒤 저장한다.

```json
{
  "skills": ["Python", "Figma"],
  "tags": ["개발", "AI·데이터"],
  "projects": [{ "title": "...", "role": "...", "period": "...", "evidence": "..." }],
  "awards": [{ "title": "...", "date": "...", "evidence": "..." }],
  "activities": [{ "title": "...", "period": "...", "evidence": "..." }]
}
```

2. `extractRequirements(공고 본문) → 필요 항목` (지원 준비). 항목 키는 고정 목록에서만 고른다. 목록에 없으면 `other`로 두고 공고 문구를 그대로 쓴다. 근거 문장이 없는 항목은 내지 않는다.

```json
{
  "fields": [
    { "key": "name", "required": true, "evidence": "..." },
    { "key": "other", "label": "포트폴리오 링크", "required": false, "evidence": "..." }
  ],
  "documents": [
    { "name": "재학증명서", "condition": "...", "evidence": "..." }
  ]
}
```

고정 키: `name` `phone` `email` `studentId` `school` `major` `year` `birthDate` `portfolioUrl` `certificates` `awards` `activities`

3. 공고를 분류할 때 `ai.tags`도 아래 태그 목록에서 붙인다(10절).

**태그 목록 (초안, 팀이 확정)**

`개발` `AI·데이터` `디자인` `영상·콘텐츠` `마케팅·홍보` `기획·창업` `글쓰기` `외국어·글로벌` `금융·경제` `공공·정책` `환경·사회` `봉사` `연구` `스포츠·문화`

**추천 순서 (코드)**

점수는 겹치는 태그 수, 관심 분야 일치, 대상 학년·전공 일치를 더해서 낸다. 마감이 지난 글은 뺀다. 카드에는 "내 태그 「AI·데이터」와 겹침"처럼 추천 이유를 코드로 붙인다. 가중치는 현찬이 정하고 표본으로 확인한다. (규칙은 `backend/app/ai/recommend.py`에 구현했고, 피드 연결은 다음 단계다)

**우선순위**

| 단계 | 내용 | 시작 조건 |
|---|---|---|
| P0 | 6절의 공지 수집, 피드, 알림 | 바로 |
| P1 | 가입과 필수 동의, 내 이력 수기 입력, 태그 맞춤 추천 | 백엔드는 P0 알림이 끝까지 1회 돈 뒤. 프론트는 P0 화면이 mock으로 돌면 먼저 시작해도 된다 |
| P2 | 포트폴리오 PDF 분석(선택 동의, 가리기 포함) | P1 추천이 돈 뒤 |
| P3 | 지원 준비 패널(필요 항목, 내 값, 복사 버튼) | 시간이 남으면 |

추천을 지원 준비보다 앞에 둔 이유는 공지 피드와 바로 이어져서 데모 흐름이 자연스럽기 때문이다. 순서는 팀이 정한다(16절).

## 8. 외부 플랫폼 처리 (팀 결정 필요)

팀은 링커리어·캠퍼스픽을 넣기로 했다. 그런데 링커리어 약관에서 위험 신호가 나와서 처리 방식을 다시 정해야 한다.

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A (추천)** | MVP는 학교 게시판만 쓴다. 외부 플랫폼은 로드맵에 "제휴·공식 API 문의"로 둔다 | 약관 위험이 없다. 발표 Q&A에서 방어하기 쉽다 | 외부 정보 범위가 좁다 |
| B | 사용자가 외부 공고의 내용을 복사해 붙여 넣으면 AI가 요약하고 마감일을 뽑아 내 피드에 저장한다 | 우리 서버가 외부 사이트에 접근하지 않는다. 데모가 된다 | 사용자가 복사하는 수고가 남는다. 링크만 받아서 서버가 페이지를 가져오는 방식은 39조 2호 문구에 걸릴 수 있다 |
| C | 자동 수집 | 정보가 가장 많다 | 링커리어 약관 위반. 심사에서 "크롤링 합법이에요?"를 맞는다 |

추천은 A이고, 시간이 남으면 B를 더한다. 캠퍼스픽은 금지 근거를 못 찾았으니 약관을 확인한 뒤 따로 정한다.

## 9. 시스템 구성 (제안, 팀 스택에 맞춰 바꿔도 됨)

```
[수집기: 주기 폴링] → [정규화·중복 제거] → [AI 처리: 분류·요약·추출] → [DB]
                                                        ↓
                    [API 서버] ← 피드·상세·구독 → [웹 프론트 (모바일 우선)]
                         ↓
                    [알림 발송: 구독 조건에 맞는 새 글만]
```

- **폴링 간격**은 10분을 제안한다(학교 서버 부하를 고려). 팀이 말한 「실시간」을 몇 분으로 볼지는 16절에서 정한다. 데모용으로 "지금 수집" 엔드포인트를 따로 둔다.
- **중복 제거 키**는 `출처ID + 글번호`다.
- **알림 채널** 후보는 아래와 같다. 오늘은 팀이 직접 돌려 보고 되는 것 하나만 고른다.
  - 웹 푸시: 앱 설치가 필요 없다. iOS는 홈 화면에 추가한 경우에만 된다고 알고 있는데 **추정**이라 확인이 필요하다.
  - 텔레그램이나 디스코드 봇: 설정이 쉬운 편이라고 **추정**한다. 국민대생이 많이 쓰는 채널인지는 모른다.
  - 카카오 알림톡: 사업자 절차가 필요하다고 **추정**해서 오늘은 제외한다.

## 10. 데이터 모델과 API 계약 (프론트·백엔드 병렬 작업용)

**백엔드는 첫 30분 안에 이 계약을 확정하고 `mock/notices.json`을 올린다. (계획은 실제 공지 20건이었고, 실제로는 가상 공고가 올라갔다. AI 정확도는 실제 공지 20건으로 따로 쟀다)** 프론트는 그걸로 바로 화면 작업을 시작한다.

### 공지 (Notice)

아래 `ai` 안의 값(요약, 마감일, 대상, 신청 방법)은 형식을 보여 주려고 넣은 **예시**다. 실제 추출 결과가 아니다. 제목, 주소, 날짜, 부서는 2026-10-03 학사공지 목록에서 확인한 값이다.

```json
{
  "id": "kmu-4-12465",
  "source": { "id": "kmu-academic", "name": "학사공지", "group": "본부" },
  "title": "2026학년도 2학기 제1전공 변경신청 안내",
  "url": "https://www.kookmin.ac.kr/user/kmuNews/notice/4/12465/view.do",
  "postedAt": "2026-10-03",
  "department": "교무팀",
  "pinned": false,
  "fetchedAt": "2026-10-03T12:00:00+09:00",
  "ai": {
    "status": "done",
    "categories": ["학사"],
    "tags": [],
    "summary": ["...", "...", "..."],
    "deadline": { "date": "2026-10-16", "time": "17:00", "evidence": "10/16 금 17:00" },
    "audience": { "years": [], "majors": [], "text": "제1전공 변경 희망자" },
    "apply": "온라인 신청 (원문 참고)"
  }
}
```

- `ai.status`는 `pending`, `done`, `failed` 중 하나다. `failed`이면 원문 링크만 보여 준다.
- `deadline`, `audience`, `apply`는 모르면 `null`이다. 빈칸을 그럴듯한 값으로 채우지 않는다.
- `tags`는 6-1절 태그 목록에서만 고른다. 맞는 태그가 없으면 빈 배열이다.
- 작성자 이름 필드는 두지 않는다.

### 분야 (categories, 고정 목록)

서비스 분류는 `학사·생활` `졸업` `장학` `취업` `행사·대외활동` `기타` 6개다. 서버(`backend/app/core/config.py`)와 화면(`frontend/lib/shared/lib/feed_config.dart`)이 같은 목록을 쓴다.

AI 모듈(`backend/app/ai/config/categories.json`)은 처음 계획한 10개(`학사` `장학` `공모전·행사` `채용·인턴` `특강·교육` `국제교류` `봉사` `생활·시설` `시스템` `기타`)로 정확도를 쟀다. 서비스 6개로 옮기는 표는 같은 파일의 `serviceMap` 이고, enrich 결과에 `serviceCategories` 로 같이 싣는다(「졸업」은 제목에 졸업이 있으면 코드가 붙인다).

AI 모듈의 게시판별 기본값은 학사(4)→학사, 장학(7)→장학, 공모·행사(9)→공모전·행사, 교외채용(11)→채용·인턴, 특강(6)→특강·교육이다. AI가 여기에 태그를 더한다.

```json
  "userId": "u_123",
  "major": "소프트웨어학부",
  "year": 3,
  "categories": ["공모전·행사", "장학"],
  "sources": ["kmu-academic", "cs-notice"],
  "keywords": ["AI"],
  "tags": ["AI·데이터", "개발"],
  "channel": "webpush"

```

구독에는 이름, 학번, 연락처를 넣지 않는다. `tags`는 내 이력에서 나온 추천 태그다.

## 11. AI 처리 규칙

- **입력**은 제목과 상세 페이지 본문 텍스트다. 첨부파일은 넣지 않는다. (서버 구현은 첨부 pdf·hwp 글자도 넣는다. 본문이 포스터 이미지뿐이면 AI 모듈이 이미지 글자를 먼저 읽는다)
- **출력**은 10절 `ai` 객체 스키마로 고정한다. 스키마에 맞지 않으면 1회 재시도하고, 그래도 안 되면 `failed`로 둔다.
- **같은 글은 다시 처리하지 않는다.** 결과를 캐시해서 비용을 막는다.
- **개인정보 값은 프롬프트에 넣지 않는다.** 예외는 선택 동의를 받은 포트폴리오 분석 하나다. 이때도 전화번호·이메일·학번 형태는 브라우저에서 가린 뒤 보내고, 서버는 요청 본문을 저장하거나 로그에 남기지 않는다. 머지 전에 AI 호출 코드에 프로필 값이 들어가지 않는지 확인한다.
- **API 키와 크레딧** 사용은 현찬 승인 후에 한다. 키는 `.env`에만 두고 커밋하지 않는다.
- **정확도는 숫자로 잰다.** 실제 공지 20건의 마감일을 사람이 원문을 보고 먼저 적어 두고, AI 결과와 대조한 수치를 발표에 쓴다.

백엔드 혼자 수집, API, 알림, AI를 다 맡으면 과부하가 걸린다. 그래서 AI 처리를 현찬이 함수 하나로 떼어 맡는 안이다. 현찬 몫은 제안이고 「남는 것 붙이기」보다 범위가 크니 줄여도 된다. v0.2 기능으로 백엔드 일이 늘어서(가입, 동의, 삭제, 추천), AI 함수와 추천 규칙과 동의 문구는 백엔드 밖에서 맡는 안이다.

**Git 규칙:** 저장소 맨 위 `AGENTS.md` 2절을 따른다. 각자 자기 이름 브랜치(현찬은 `HC`)에서 작업하고, PR을 merge commit으로 main에 머지한다. 머지 담당은 팀이 정한다.
